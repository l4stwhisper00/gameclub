# Архитектура карточных игр GameClub

Статус: проектирование первого серверного карточного движка (Дурак). Документ фиксирует общие границы безопасности и расширения для следующих карточных игр. Он не означает, что Дурак уже реализован.

## 1. Область первой реализации

Первая игра — классический подкидной Дурак:

- 2–6 участников;
- колода 36 карт (6–Туз), по 6 карт на старте;
- случайный козырь, карта козыря остаётся нижней картой колоды;
- атака, защита, подкидывание карт, взятие стола;
- добор до шести карт в установленном порядке;
- завершение после опустошения колоды и рук: последний игрок с картами проигрывает;
- без переводного варианта в первой версии.

Правила должны быть единообразными для всех клиентов. Клиент только отображает состояние и отправляет намерение выполнить действие.

## 2. Границы доверия

### Клиент

Клиент может:
- получить публичное состояние партии;
- получить только собственную руку;
- отправить действие и ожидаемую ревизию;
- подписаться на изменение публичного состояния через Supabase Realtime.

Клиент не определяет легальность действий, порядок хода, результат партии, раздачу, козырь или состав чужих рук. Клиент не записывает состояние игры напрямую в PostgreSQL.

### Edge Function

Отдельная Edge Function карточных игр — серверная точка входа. Она:
1. проверяет Bearer-токен через Supabase Auth;
2. проверяет существование комнаты, её game_id и членство пользователя;
3. загружает авторитетное публичное и приватное состояние;
4. проверяет ожидаемую revision;
5. проверяет действие по серверному движку и правилам конкретной игры;
6. атомарно сохраняет новую публичную и приватную части;
7. возвращает публичное состояние и только руку вызывающего пользователя.

Ни один параметр от клиента (карта, игрок, фаза, счётчик, козырь или результат) не считается доверенным.

## 3. Публичное и приватное состояние

Существующая таблица `public.club_room_game_states` имеет политику SELECT для всех участников комнаты. Поэтому помещать в её JSONB поле `state` руки игроков, порядок колоды или иные секреты нельзя: любой участник комнаты сможет прочитать весь JSONB.

Публичная часть в `club_room_game_states.state` содержит только:
- идентификатор и версию партии;
- фазу и статус;
- порядок активных игроков и текущие роли атаки/защиты;
- открытые карты на столе и их покрытие;
- козырную масть и открытую козырную карту;
- количество карт в руках каждого игрока;
- количество карт в колоде;
- открытый сброс, если он используется правилами;
- публичные события и итог партии.

Приватная часть должна храниться отдельно в закрытой схеме PostgreSQL, например `private.card_game_secrets`:
- ключ комнаты и игры;
- руки игроков, индексированные по user_id;
- точный порядок оставшейся колоды;
- любые будущие скрытые данные конкретной карточной игры.

Для приватной таблицы: включить RLS, не выдавать права `anon` и `authenticated`, предоставить доступ только серверной роли. Схему `private` не добавлять в список схем Data API.

Поскольку клиентский Data API не должен читать приватную схему, серверная функция использует только серверные RPC-обёртки, доступные исключительно `service_role`. Для таких RPC необходимо явно отозвать EXECUTE у PUBLIC, anon и authenticated и выдать EXECUTE только service_role. Сами функции не должны становиться публичным способом обхода RLS.

## 4. Атомарность и защита от гонок

Публичное состояние, приватные руки и порядок колоды должны изменяться одной транзакцией. Два параллельных запроса не должны оба применить ход к одной ревизии.

Предлагаемый протокол:
- Edge Function рассчитывает переход из состояния revision N;
- серверный commit-RPC получает ожидаемую ревизию N, публичный снимок и приватный снимок;
- RPC блокирует/проверяет запись партии и выполняет compare-and-swap;
- публичная ревизия становится N+1 и приватные данные записываются в той же транзакции;
- при несовпадении ревизии транзакция отклоняется с конфликтом, клиент загружает актуальное состояние.

RPC работает с правами вызывающей роли (`SECURITY INVOKER`) и доступен только `service_role`; если реализация потребует `SECURITY DEFINER`, это отдельное обоснованное решение с фиксированным пустым search_path, полными именами объектов и отзывом EXECUTE у всех клиентских ролей.

## 5. Контракт состояния и расширяемость

Общий транспортный контракт карточных игр:

- `start` — начать партию (только ведущий, допустимое число игроков);
- `state` — получить публичное состояние и собственную приватную руку;
- `action` — выполнить действие игры с expected revision;
- `leave` — корректно обработать выход участника;
- `return_to_lobby` — завершить игровую сессию и вернуть комнату в лобби по разрешённому правилу.

Внутренний движок каждой игры реализует одинаковые операции: создать начальное состояние, проверить и применить действие, сформировать публичную проекцию, сформировать приватную проекцию игрока и обработать уход участника. Специфические правила не должны попадать в общий транспортный слой.

Для Дурака типы действий: `attack`, `defend`, `take`, `finish_attack`. Сервер сам определяет, кто атакует, кто защищается, какие карты можно подкинуть/покрыть, сколько атак допустимо, когда разрешён добор и кому принадлежит следующий ход.

## 6. Выход участника

Выход/удаление участника во время активной партии не должен оставлять игру в состоянии, где ход принадлежит отсутствующему игроку или приватная рука остаётся доступной.

Первая версия использует предсказуемое правило: уход участника во время активной партии завершает её статусом `abandoned` без победителя, очищает приватные секреты партии и публикует событие в общей комнате. Это безопаснее, чем незаметно менять порядок ходов или передавать карты. Изменение членства и завершение партии должны быть согласованы транзакционно; обработка должна покрывать как самостоятельный выход, так и удаление участника ведущим.

Ограничение существующей модели сохраняется: ведущий не может покинуть собственную комнату через текущий RPC. Назначение администратора и права ведущего не меняются.

## 7. Realtime и клиентская синхронизация

Realtime передаёт только изменения публичной строки `club_room_game_states`. Получив ревизию N+1, клиент запрашивает у Edge Function свою приватную руку. События применяются только если их revision новее уже отображённой.

Приватные руки никогда не рассылаются через общий Realtime payload, общий чат, метаданные комнаты или публичный JSONB. Нельзя подписывать всех участников на таблицу приватных секретов.

## 8. Проверки перед включением игры

Обязательные серверные тесты:
- 2 и 6 игроков, случайная раздача без дубликатов;
- все четыре масти и определение козыря;
- неверный ход, чужой ход, неверная карта и повторный запрос;
- побитая/непобитая атака, подкидывание и предел числа карт;
- взятие стола, добор и порядок добора;
- пустая колода, победитель и последний проигравший;
- выход атакующего, защищающегося и третьего игрока;
- две конкурирующие команды с одинаковой revision;
- попытка прочитать чужую руку через Data API, Realtime и прямой запрос к таблицам;
- повторное подключение и восстановление состояния после потери сети.

Проверки безопасности должны подтверждать, что обычные участники читают только публичное состояние и собственную руку через серверный ответ. До прохождения этих проверок игру нельзя считать готовой к публикации.

## 9. Ограничения изменений

- Не удалять и не переименовывать существующие таблицы.
- Не изменять `profile-game-statistics` и `supabase/game-statistics.sql`.
- Не менять администраторские права и не добавлять клиентские способы их назначения.
- Не помещать секретные данные в `club_room_game_states.state`.
- Не ослаблять серверную валидацию ради скорости.
- Все изменения БД — отдельной миграцией после проверки документации Supabase, RLS и advisors.
